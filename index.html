01

ADOPTION LEVELS

The scope of delegated decisions

A license does not define maturity. A repeatable team workflow does.

WORKING MODEL · THE LEVEL IS PROCESS SPECIFIC

Five adoption levels

1Promptinganswer
2Assisted codingedit
3Agentic codingtask
4Spec drivencontract
5Bounded autonomyprocess

A workshop classification based on the source material. This is not an industry standard.

1–2

PROMPTING · ASSISTED CODING

A human controls the change

Claude explains code, proposes snippets, and makes small edits. A human selects the context and evaluates every output.

BoundaryNo independent execution of a multi-step task.
3

AGENTIC CODING

The agent completes a task

It investigates the repository, plans, edits multiple files, runs commands, and uses test results as feedback.

ControlPlan, permissions, tests, and diff review.
4

SPEC DRIVEN DEVELOPMENT

The specification drives the work

The problem, acceptance criteria, and verification method form a contract. Team knowledge lives in the repository.

ControlVersioned instructions, skills, hooks, and quality gates.
5

BOUNDED AUTONOMY

Automation across the process

Agents handle a task queue or part of a pipeline. Autonomy runs in a sandbox with a cost limit and a clear stopping condition.

Entry criteriaA stable process, observability, and quality evidence.

MOVING UP THE CURVE

Autonomy grows after the gates are met

Repeatabilitythe task follows a known pattern
Verificationthe outcome can be checked
Isolationan error has a small blast radius
Observabilitydecisions and cost leave a trace

Standardize first. Automate next. Increase autonomy after the workflow is measurable.

SPEC DRIVEN DEVELOPMENT IN PRACTICE

Three frameworks operationalize the contract

GitHub Spec KitSpecification lifecycle

Turns requirements into a specification, plan, tasks, implementation, and convergence checks.

GSD CoreGit. Ship. Done.

Uses a five-step loop: discuss, plan, execute, verify, and ship. Durable artifacts carry context between phases.

BMad MethodAdaptive SDLC workflows

Scales planning to the change and adds specialized product, architecture, development, and testing perspectives when needed.

Sources: GitHub Spec Kit, Open GSD, and BMad Method. Same principle, different process depth.

ARCHITECTURE

An agent is a feedback loop

The model makes each next decision from observations returned by the environment.

MINIMAL ARCHITECTURE

Components of an agentic system

Goal + contractwhat done means
contextMODEL + ORCHESTRATORworking memory
Toolsfiles · shell · API · MCP
Environmentrepo · tests · systems
Verifiertest · policy · human

Pattern: augmented LLM and agent loop, Anthropic.

THE AGENT LOOP

Every step should produce an observation

  1. 1inspect state
  2. 2choose an action
  3. 3use a tool
  4. 4read the result
  5. 5assess progress
  6. 6stop or repeat

A test result, diff, or API response provides stronger evidence than the model's confident tone.

DETERMINISM AND AUTONOMY

A workflow knows the path. An agent chooses the path.

Workflow

Known sequence

Fixed steps, predictable cost, and straightforward failure analysis. Best when the process can be described in advance.

Agent

Dynamic decisions

Chooses tools and the number of steps. Needs limits, observability, and a stopping condition.

ARCHITECTURE PATTERNS

Complexity carries an operating cost

Chaininga fixed sequence of steps
Routingselection of a specialized path
Parallelizationindependent tasks or votes
Orchestratordynamic work decomposition
Evaluatoriteration against criteria

Source: Anthropic, Building Effective AI Agents.

04

HALLUCINATIONS AND GUARDRAILS

Trust requires evidence

A confident response does not predict a correct outcome.

HALLUCINATIONS IN CODING

Three forms of a false view of reality

False fact

A nonexistent API, flag, library, or version behavior.

False state

An assumption about code, files, or the environment without inspection.

False completion

A success claim without a test, diff, or state observation.

In an agentic system, a wrong answer can become a wrong action.

EVIDENCE CONTRACT

Every claim needs a verifiable source

Claim“The tests pass”command output
Claim“The API supports this option”current documentation
Claim“The change is minimal”diff + stat
Claim“The problem is solved”acceptance criteria

When evidence is missing, the response should state its uncertainty and the next verification step.

GUARDRAIL STACK

Soft guidance supports hard boundaries

4 · Processreview, owner, rollback, incident
3 · Verificationtests, schemas, policies, evals
2 · Runtimepermissions, hooks, sandbox, limits
1 · Contextprompt, CLAUDE.md, rules, spec

Anthropic separates defenses across the model, environment, and external content.

GUARDRAILS OUTSIDE CONTEXT

Boundaries that survive a long session

Do not read secretsRead deny + no secret in the workspace
Do not run destructive actionsBash deny + PreToolUse hook
Do not publish without approvalno permission and a separate identity
Stop the costbudget, time, and iteration limits

The prompt describes intent. The permission system limits actual capability.

EXTERNAL CONTENT

Any document can become a control input

issue / README / website1instruction hidden in content2model changes the plan3tool executes an action
Limit sourcesSeparate data from instructionsRestrict toolsRequire approval for side effects

MCP and connectors expand reach. They do not replace permission policies or a sandbox.

PARALLELIZATION

The lightest mechanism that solves the problem

Subagent

Research, logs, review, or a side task. The result returns as a summary.

Agent team

Human team

FINOPS AND REGRESSIONS

Cost is an architecture property

Every branch of work, extra context block, and additional attempt consumes budget.

COST ANATOMY

What increases the bill

contextinput tokens× modelrate and effort× stepsiterations and tool calls× branchessubagents and teams

Optimizing one prompt has little impact when the system runs too many steps or agents.

FINOPS LEVERS

Remove work that adds no information

Fresh session/clear between unrelated tasks
Right modela cheaper model for simple tasks and workers
Context on demandskills, scoped rules, limited MCP
Short loopspecific AC, fast tests, iteration limit
Measurement/usage, telemetry, cost per successful task

Source: Claude Code Docs, Manage costs effectively.

THREE DIFFERENT LEVERS

They reduce different kinds of waste

RTKterminal to input

Filters noisy command output before the model sees it.

Cavemanagent to output

Shortens response prose while preserving technical substance.

Ponytaildecision to code

Pushes toward the simplest solution and actively looks for code to remove.

RTK reduces shell output, not the whole bill. Caveman can add overhead to an answer that is already short. Links: SOURCES.md.

DEGRADATION AND REGRESSION

The same workflow can perform worse tomorrow

Modela new version or routing change
Contexta growing CLAUDE.md or conflicting rules
Toolsan API, schema, or permission change
Datanew cases and input drift
Processweaker review or tests

Quality regression requires diagnosis of the whole system, not only the model.

REGRESSION PROTECTION

A stable task set and controlled rollout

  1. 1golden set from real tasks
  2. 2multiple trials per case
  3. 3outcome and trajectory grading
  4. 4canary with a small group
  5. 5monitoring and rollback

Record the model version, configuration, available tools, and trace. Without them, comparison becomes anecdotal.

Sources: Anthropic, Demystifying Evals for AI Agents and Postmortem of Three Recent Issues.

FAILURE ANALYSIS

The trace explains how. The outcome confirms whether.

TRACE

prompts, context, decisions, tool calls, results, and corrections

OUTCOME

repository state, tests, artifact, external effects, and final cost

DIAGNOSIS

the first wrong step, missing signal, and ineffective barrier

Anthropic separates the transcript or trajectory from the final outcome in agent evaluations.

FAILURE TAXONOMY

Classify the failure before changing the system

C1unclear contractimprove the spec
C2missing contextadd a source
T1wrong toolimprove the interface
M1reasoning errormodel or decomposition
V1weak verificationadd a grader
O1work conflictchange ownership

Analyze the first error, not the last visible symptom.

COST FAILURE

A correct outcome can still be uneconomical

MetricCost per accepted taskconnects spend with value
SymptomMany tokens with no outcome changestale context or a loop
SymptomMany rejected attemptsweak contract or grader
SymptomParallel work without lower lead timecoordination costs exceed the gain

METRICS

Measure the system, not generated lines

Outcomepass rate · defects · rollback
Effortreview time · corrections
Flowlead time · throughput
Costtokens · cost / success
Safetyblocks · boundary violations
Learningrepeated errors · rule updates
